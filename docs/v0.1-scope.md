# v0.1 Scope

What the first MVP of `phase0-bootstrapper` does, what it deliberately leaves
out, where it is weak today, and where it goes next. Read this with
[`phase0-contract.md`](phase0-contract.md) (the formal contract) and
[`safety-policy.md`](safety-policy.md) (the read-only rules).

## What v0.1 supports

- **Read-only repository scan** of a local directory: a size-limited,
  symlink-safe walk that prunes caches/vendored/build dirs. The only filesystem
  write is the output pack.
- **Project-type detection** from structure and manifests: Python,
  Node/TypeScript, Terraform/IaC, dbt, data pipeline (notebooks), and a
  "mixed repo" label when several ecosystems coexist.
- **Important-file detection**: READMEs, Python/Node manifests, Dockerfiles,
  docker-compose, Makefile/Taskfile, GitHub Actions workflows, Terraform, dbt,
  notebooks, tests, ADRs, and `AGENTS.md`.
- **Command detection without execution**: npm `scripts` and Makefile targets
  are recorded as `[FACT]` (`npm run <x>` / `make <x>`); tooling inferred from
  `pyproject.toml` (pytest/ruff/mypy) is `[INFERENCE]` with a confidence level.
  **No command is ever run.**
- **Secret-file safety**: `.env`, private keys, and credential files are flagged
  by **existence and location only** and recorded as a risk — their contents are
  never read, rendered, or printed (`.env.example`/`*.pub` are treated as safe).
- **The 11-file Phase 0 pack** written to `<repo>/.ai/phase0/` (see
  [`output-schema.md`](output-schema.md)): `manifest.yaml` + 10 markdown files
  (repo map, architecture, entrypoints, commands & tooling, decision log,
  assumptions & open questions, risk register, safe-change boundaries, agent
  handoff, evidence map).
- **Epistemic discipline**: every claim is tagged `[FACT]`/`[INFERENCE]`/
  `[ASSUMPTION]`/`[OPEN]`; every `[FACT]` cites an `E#` that resolves in
  `evidence-map.md`; generation fails if a cited `E#` is dangling
  (`Phase0Report.validate()`).
- **Two delivery surfaces**: the `phase0` CLI (`scan` with `--output-dir`,
  `--dry-run`, `--force`, `--format text|json`) and an Agent Skill (Claude Code
  and a portable copy for Codex/other agents).
- **Zero runtime dependencies** — Python standard library only.

## What v0.1 intentionally does NOT support

- **No LLM integration.** Detection is deterministic and rule-based. No model
  calls, no prompts, no API keys.
- **No external services or network calls.** No vector DB, no embeddings, no
  remote storage, no telemetry. Everything runs locally and offline.
- **No code execution of any kind** on the target repo — no build/test/install/
  run/format/lint/codegen, no project scripts, no `git` writes.
- **No deep code analysis.** No AST parsing, import-graph resolution, call
  graphs, or data-flow analysis. Architecture is inferred from directory
  structure and is explicitly low-confidence.
- **No purpose/prose extraction.** READMEs are located and cited, not
  summarized.
- **No remote repositories.** The input is a local path; cloning is out of
  scope.
- **No writing outside `<repo>/.ai/`.** The tool refuses to write to the repo
  root, into the source tree, or to a system/home root.

## Known limitations

- **Entrypoint detection is shallow** — derived from detected commands, not from
  reading code. The primary runtime entrypoint is raised as an `[OPEN]`
  question rather than asserted.
- **Architecture is name-based** — top-level `src/lib/app/...` dirs are listed
  as candidate components at low confidence; no responsibilities are proven.
- **Command inference is heuristic** — pyproject tooling implies a convention,
  not a verified command; these stay `[INFERENCE]`.
- **Language detection is extension-based** — presence, not behavior; embedded
  or unusual languages may be missed.
- **Large/binary files are skipped** (>1 MB or containing NUL bytes), so signals
  living only inside them are not captured; the sampling boundary is recorded.
- **Git metadata is loose-ref only** — HEAD is read from `.git` files without a
  subprocess; packed refs and worktrees may yield an empty commit.
- **Single-repo, single-pass** — no monorepo-aware sub-project splitting and no
  incremental/diff mode.

## Future roadmap (not in v0.1)

Candidate directions, roughly in priority order. None imply LLM or external
service dependencies unless explicitly stated.

- **Deeper, still-deterministic analysis**: import graphs and real entrypoint
  detection per ecosystem (e.g. `[project.scripts]`, `main`/`__main__`,
  `package.json` `bin`, Dockerfile `CMD`/`ENTRYPOINT`).
- **Lockfile + dependency surfacing** (pinned vs. unpinned) as risks.
- **Monorepo awareness**: detect and scope multiple sub-projects.
- **Richer readiness scorecard** and a `--strict` evaluator exit code for CI.
- **Incremental re-scan** that diffs against an existing `.ai/phase0/`.
- **Optional, clearly-bounded** integrations (e.g. packed-ref git reading) kept
  behind the read-only contract.

LLM-assisted summarization, if ever added, would be a separate, opt-in layer on
top of this deterministic core — never a requirement to produce the pack.
